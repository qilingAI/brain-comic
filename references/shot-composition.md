# 第三步：漫画画面组合与参考图绑定

第三步包含两个内部环节：先写逐张组合提示词，再使用对应参考图片生成漫画画面。用户明确说调试或只检查prompt时，完成前一环节即停止；正常执行第三步则按主技能的API优先顺序衔接生图。不再把生图单独叫第四步。

## 输入与范围

- 第一阶段用户选定的完整内容稿；剧情、对白与旁白以此为准。
- 第二阶段的资产表与 `images/manifest.json`。使用状态为 `generated` 的生成资产或 `provided` 的用户角色原图，文件必须确实存在；以清单当前选中版本为准，不按文件名猜测版本。用户IP不能因为没有“生成”状态就被漏掉。
- 独立风格配置 `styles.json` 和本主题style_id。不把旧风格正文写入资产或布局模板；生成时重新解析当前选择。
- 同一主题内操作。不要重新生成已有资产、修改第一步对白、添加新剧情或把单张元素补成跨图参考图。

用户未指定漫画画幅时，先用单张3:4竖幅作可修改的默认设置，写在交付文件开头；画幅属于画面设置，不属于风格。每张为一幅连续剧情画面，不继承资产设定图的分区。

## 稳定标记和每张传图顺序

模板使用精确标记 `{{ref:C01}}`、`{{ref:S01}}` 等引用资产ID。不要预先把某个资产永久命名为图1；同一C01在不同请求中可能是不同槽位。

每张保存有序 `references` 数组，每条包含：

```json
{
  "asset_id": "C01",
  "marker": "{{ref:C01}}",
  "image_index": 1,
  "file": "images/assets/C01.png",
  "sha256": "实际图片的SHA256"
}
```

`file` 相对于本主题的第三步JSON文件所在目录。读取实际图片时解析为绝对路径，不能把本机绝对路径当作通用API地址。

按个人、群像、场景、道具顺序排列，同类按稳定ID排序。每张只包含实际需要的资产，同一ID只占一个槽位；多次提及或群像内多个人不会重复上传同一图。`image_index` 从1连续递增，与本次上传顺序完全一致。

在即将提交请求时，使用该张的引用表，将 `{{ref:C01}}` 精确替换为 `图1` 等标签，并按references相同顺序传入图片文件、字节或服务允许的图片输入。不是把图片编码直接插进prompt标记。标签只是说明图片顺序，不假设任何供应商有相同API字段。

如果供应商使用其他图片标签，只在适配层变换表达和传图格式，模板中的资产ID保持不变。不得只替换文字而不实际传图。如果工具有参考图片数量上限，先说明限制，不删除资产；可以用共享脚本的 `--max-reference-images 数量` 将部分原图无缩放地拼成带REF-A/REF-B等区名的输入素材板，并将实际prompt对应为“图1的A区域”等。API的原始逐图绑定不变，执行清单额外记录实际输入图、区名、路径和摘要。素材板仅是输入包装，不是重新生成参考图，原始资产文件不修改。只有使用此包装时需要Pillow。若宿主完全不支持多图且也无法提供完整参考输入，应说明限制并停止，不能暗中漏图。

## 参考图继承什么

- 个人锁定脸、发型、服色、护甲和身体特征；表情、姿势、视线和当前手持物按本张剧情安排。三视图是同一人物的不同角度，不画成三个人。
- 用户IP由其实际原图锁定身份，优先于默认Q版比例与临时补足的通用人物描述；保留物种、轮廓、脸部、身体比例、主色、标记和用户锁定特征。角色卡的既有排版不作为最终画面布局；有意换装依用户指令。只传角色描述而不传原图不算复用了IP。模板中清除与用户IP冲突的旧体貌/服装描述，避免一边要求保留原图、一边指定另一个角色。用户只指定一个人物时，其他人物不跟着替换。
- 群像继承共同服饰、阵营配色和成员自然差异，不把整张白底人物目录贴入画面。实际人数与站位由本张需要决定。
- 场景继承建筑造型、材质和空间连接；门的开合、人物位置与视角按剧情调整。场景图的四宫格只是视角参考，最终画面不是四格拼图。画面内的屏幕左右不等于世界坐标方向，不能通过镜像把城内外关系颠倒。
- 道具继承轮廓、材质、配色和结构；参考图上同一物体的多视角不表示本张要画多个实物。可以按剧情拿起、放下或合理遮挡，不能无故改成另一种道具。
- 不把参考图里附带的背景、重复视图、多余文字或无关个体一起带入。本张未出现的角色或道具，即使某张参考图里有，也不要添加。
- 多张场景参考图可能包含同一座建筑。要说明本镜头真正可见的部分；例如从本城墙向城外看，不能把城外全景参考里的同一城门再画成远处第二座城。参考图只是识别信息，不是每个可见元素都必须重画。

## 每张提示词内容

1. 写明生成一幅完整剧情画面，使用当前风格和画幅。
2. 用标记说明每个参考图的身份和用途，例如 `{{ref:C01}}是阿禾，只取人物外观；{{ref:S01}}是城门，仅取建筑结构`。
3. 明确本张场景、景别、观察方向、主体位置、一个主要动作、视线和必要表情；重要关系要写清“谁拿什么、看什么、物件放在哪”。
4. 自动识别的单张元素直接描述其形状、服饰或环境，不虚构引用标记；用户提供的单次出场角色可以引用已导入的真实原图。地图里的营地或“援军”标记仍是纸上内容，不让它们变成现实出场的军队。
5. 白底只用于第二步设定图；第三步采用本张真实环境。只为旁白和气泡留出可读空间，不为标题预留区域，不要求整张白底。
6. 对白与旁白逐字保留在独立text字段，并在完整prompt中明确文字位置与对白归属；画面里的文字严格按下一节“画面内文字”执行。

可以为手持地图等物件补充不改变剧情的承托位置，但须在交付说明中标记为画面布置补全，不新增跨图资产。对白谈及尚未发生的行动，不要提前画成已经发生。

## 画面内文字：只留对白和一条旁白

生成的画面里，文字只有两种：人物对白气泡，和一条旁白。其余一律不画。

- **旁白整张只允许一条。** 位置统一放顶部或底部，第一阶段没定就在本阶段开始前定一次、全篇一致；不能出现第二条旁白或额外说明小字。prompt 里只描述这一条旁白和它的唯一位置。
- **对白放人物附近的气泡。** 尾巴指向说话人，阅读顺序从上到下，不让气泡尾巴指错人。
- **免责声明和 AI 标识绝不写进画面。** “史实漫画示意”“非现场实录”“人物与对白为虚构演示”“本故事纯属虚构”这类说明，以及“内容由AI生成”标识，由发布方在正文或平台声明里写，不写进 prompt、不画进图片。
- **不画编号、标题和水印。** 图号、“图1”“第X张”、标题、小标题、页码、日期、平台名、署名、Logo、二维码、水印都不画；`images/comic/001-xxx.png` 的文件编号只用于排序，不是画面内容。
- **不设标题区。** 留白只给旁白和气泡；拟声词、箭头、批注等额外文字也不加。本张原稿明确指定在物件上出现的字（如匾额）按原稿写。
- **写进 prompt。** 这些禁止项要直接写在每张 prompt 里；出图后只要出现上面任何一类文字，判不合格重做，不靠裁切或打码补救。

## 交付与检查

主题内交付 `stage3-prompts.json` 和便于审阅的 `stage3-prompts.md`：JSON保留每张的 `prompt_template`、有序references、原稿text及由当前风格拼接后的 `rendered_prompt` 预览；Markdown显示引用顺序、特殊标记和画面prompt。rendered_prompt是生成快照，换风格或替换参考图后须重新编译，不将其当作风格配置源。

生成前核对每张：

- 模板中标记集合等于references中的资产集合，图片槽位连续、无重复、无缺失文件，不残留旧版本路径。
- 精确替换后没有未解析标记；同一资产始终对应同一上传槽位，原稿文字不会被替换误伤。
- 图片用途明确，没有把设定图白底、三视图、四宫格或多件展示带进剧情画面。
- 每张保留本来应出现的人物、场景、道具和单张元素；对白与旁白未改义或遗漏。
- 每张只有一条旁白，位置全篇一致（顶部或底部）；没有第二段旁白或说明小字。
- 画面里没有免责声明（史实漫画示意、非现场实录、人物与对白为虚构演示等）、AI生成标识、图号/序号、标题/小标题、页码、水印、署名、Logo、二维码。写 prompt 时就明确禁止这些内容，不靠生成后裁切或打码补救。

正常生图时逐张按主技能的API/宿主工具路由执行，生成结果先放到主题 `images/candidates/comic/` 并另记生成状态与实际prompt。检查参考图身份、空间关系、文字与内容对应：文字只核对该有的对白、唯一一条旁白和原稿指定的物件字；出现免责声明、图号、序数、标题、页脚小字或第二条旁白，直接判不合格并重做，不把带这类文字的图放进 `images/comic/`。可在 `record` 时用 `--review passed` 标记检查通过，未通过用 `--review needs_revision` 进入 `images/not-selected/comic/`，尚未检查保持pending。失败不标成功，结果不明不盲目重试。

任务准备与保存复用第二步的 `scripts/image_jobs.py`。用 `prepare --stage 3 --topic 主题目录` 读取当前风格、验证参考图及标记顺序，再输出任务；将任务prompt和reference_images一起交给同一个API/宿主工具执行路径。返回PNG后，向record传入该任务及实际文件，写入独立comic-manifest.json；不要手工另写一套图号替换或落盘代码。

用户IP与生成资产使用同一套 `{{ref:C01}}` 和图号协议。共享编译器自动为 `origin: "user_provided"` 的角色拼入身份优先约束，并把实际图片加入 `reference_images`；同一角色多次出现也每张实际传图。更换IP参考后重新编译绑定并重新生成受影响画面，旧画面和旧视频保留为历史版本。检查结果时逐个核对IP特征，不能把“已传图”当作已经保证还原。

## 图片集交付：第三步完成条件

图片集是独立交付物。用户只要图片集时，在这里完成，不调用 ffmpeg、不索要BGM，也不把视频作为获得图片的前提。

```sh
python3 scripts/image_jobs.py finalize --stage 3 --topic 主题目录
```

整理规则：

- 以 `stage3-prompts.json` 的剧情顺序和 `images/comic-manifest.json` 的当前选择为准，全部画面必须已生成且检查通过。不能按文件名里最大的v数字、修改时间或扫描目录顺序猜测最终图。
- `images/comic/` 是用户最终图片目录，恰好每张剧情一幅原尺寸图片，命名为 `001-城门前的疑问.png`、`002-城墙提供的保护.png` 等。标题中的路径符号会清理，编号始终补零以便排序。不放说明文档、参考图、拼图、草稿或多个版本。
- 未采用的旧图、失败图移动到 `images/not-selected/comic/`，参考资产旧版移到 `images/not-selected/assets/`；仍待检查的生成图使用工作目录 `images/candidates/`。归档保留原文件，不直接删除；已完成目录中没有v1/v2并排供用户自己挑选的情况。
- 整理不转绘、不压缩、不缩放原图，也不再复制一份同样的工作图。更新当前清单、第三步JSON和相关Markdown的实际路径；过往文件移动关系保存在外置collection清单中。重复整理不会新增一套重复最终图片。
- 检查画面是否重复、少图、错序；脚本另用解码后的像素摘要拦截完全相同画面，包括文件编码不同但像素相同的图片。相近构图或重复叙述仍由agent逐张检查，不靠相似度删除正常的连续漫画。发现重复要修正对应画面，不能静默删掉一张。
- 同时生成 `images/comic.zip`，压缩包内只有按序命名的最终漫画图片；`images/comic-preview.md` 用于预览，`images/comic-collection.json` 保存编号、标题、路径、哈希与移动关系，均放在最终图片目录外。

如果重新生成了某张，先检查新候选，再重新整理：新图占用该张稳定编号，旧最终图进入未采用目录。用户选择视频输出时，先完成同一份图片集，再让第四步读取同步后的当前清单；不维护两套不同的图片选择。
